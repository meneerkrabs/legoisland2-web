# Gap inventory: where the port deviates from the original

Requirement: **no approximations**. This file is the inventory (read-only pass, 2026-10-29) of everything the port simplifies, stubs, guesses or leaves out, compared with the Ghidra decompile
(`basdebeer-tools/decomp-le2/LE2.c`, `LE2.asm.txt`, `atlas.md`). Sources: all docs under `docs/re/**`, `docs/engine-api.md`, `README.md`, a grep/read pass over `src/**`, and a few new look-ups in the decompile
(timing, RNG, input, F-keys, SetupFog calls, outro) and in the game archives (particle effects per zone, `.man` files). Port-only extras (widescreen option, mods, progressive loading, URL debug parameters,
IXS-look, bots/test aids) are ignored unless they change the default 4:3 behaviour. Sizes: S = under a day, M = a few days, L = a week or more. "Evidence" is a doc section, a decompile address/line or a code line.
`UNCERTAIN` = could not be settled from the decompile; needs the x86 emulator (`src/formats/x86emu.ts`, already used as oracle for z09JST, z10RGB, z18MMP, z20DSP, z22BIP) or a design decision.

Findings from this pass that change earlier assumptions (important for planning):
* **Rumble is not a gap**: `FUN_00438518` is an empty function in this build (LE2.c "// ==== FUN_00438518": `return;`). All "rumble not ported" remarks in the zone docs can be closed.
* **Analog stick is not a gap**: `FUN_004376f9` (SDPad) reads the stick axes (`FUN_004372d2(2, 0/1)`) only to set the direction bits (beyond +-0x40), then **zeroes** `DAT_0098384c/50` (`param_2[1] = param_2[2] = 0`).
  Code that reads those variables only sees the +-0x7f values written from the digital bits (e.g. LE2.c:23349-23355). The "analogue stick not read" remarks (z08BKD, z09JST, z10RGB, z20DSP, z28HAT, z39ASB, z41MAP, z42BRP) are moot.
* **The original has a variable time step** (`FUN_00443e40`), so "fixed 30 Hz" is itself a deviation, and per-frame (unscaled) code exists. See T1.
* **The original seeds the C `rand()` with `time()`** at start-up and again in z05WAB, z17WAS and z42BRP, and uses **`srand(1)` in z22BIP**. So the sequences are not reproducible except in z22BIP (already done). See T2.
* **F10 is a screenshot key** in the original (`FUN_0040cd27` -> `FUN_00412f2f` writes `<Fotos>\Lego0000.bmp`); the port uses F9/F10 as stub aids and always has F9 live on the island. See I4.
* After the outro movie the original goes straight to the island (decompile of `FUN_008212a3`, LE2.c:256911-256921); the port inserts the credits (U2). The docs contradict each other here.

### R3. Specular lighting and per-record "shiny" flags [M] -> DONE (WP-RENDER, 2026-10-29)
* The CPU lighting of the game is ported function by function (`src/render/meshlight.ts`: `FUN_00885664` light vectors, `FUN_00885a9a`, `FUN_0088589e`, `FUN_0088612c`, `FUN_00885e33`) and verified byte for byte against the original code on the emulator (`tools/tests/render-light.mjs`, 69,120 bytes, 275 specular vertices, max difference 0).
* `FUN_004446c0(record, 1)` is extracted for every zone (`ZoneSetup.shiny`; emulated set-ups log the call; constructors of attached nodes through `extractCtorRenderCalls`) and applied to the record's parts and attached models (`Renderer.setShiny`, vertex colours + specular colours per vertex, `uSpecOn` in the shader).
  Shiny records: island AMBU / SPD0-2 / PCAR / LOON / SBRD / BRID x6, the house's trophies and Pepper (z03PPH), z04IFC's PONT, z17WAS / z60FRE Pepper, z18MMP's mummies / spiders / coffins, z21FSH's FSHM / Pepper, the hubs' characters (z07CSI 73, z23DIP 25, z40OGL 16 ...).
* **Finding**: SPECULARENABLE is on for EVERY draw (the state blocks are `D3DSBT_ALL` captures made with `SPECULARENABLE = 1`; `FUN_004090a7` sets the render state before `ApplyStateBlock`, which overwrites it): a 0x2c2 mesh shows its highlights in block 3 as well. See rendering.md 4.2.
* Closed (second pass): a scaled shiny record (non-unit matrix) makes the half vector longer than 1 and the `pow` overflow into neighbouring colour bytes: the port reproduces it bit for bit. ### R7. Static-mesh lighting is frozen at the first draw [S, UNCERTAIN effect] -> DONE (WP-RENDER, 2026-10-29)
* Per mesh object (shared by all records that use the mesh file) `Renderer.drawMesh` lights modes 0 / 4 once (first draw, with that record's matrix and the eye of that moment) and modes 1 / attachments / skinned meshes at every draw, into the mesh's own vertex-colour buffer (the shader no longer lights): the first record to draw a mode 0 mesh decides the colours of all
  records that use it, a mode 1 record re-lights the shared buffer, unlit modes keep what the buffer holds. A new zone resets the flags (`resetLighting`, a renderer light-set change re-lights). The light vectors use the record's matrix, not a group's MATL matrix, and `normalize(M . L)` (object space), not a normalised world normal: differs for non-uniformly scaled records.
* The visible consequence is where the mode is wrong: the vehicle roster and the ctor-time mode 1 records are now lit at every draw (they would have been frozen as mode 0 before), trees / props repeated with different turns share the first one's shading.

## Findings of WP-VERIFY (differential oracle tests, 2026-10-29)

Method: the original's own functions run natively from the EXE in `src/formats/x86emu.ts` next to the port, same buttons / random numbers / dt, compared tick by tick (`tools/lib/m7-*.mjs`, `tools/tests/m7-*.mjs`, run with `node tools/test-formats.mjs --only <name>`; every test takes dt as a parameter for BOTH sides and runs at dt = 1 and dt = 0.5). ### Global result: the original runs the x87 in 24-bit precision
No `SetCooperativeLevel` passes `DDSCL_FPUPRESERVE`, so Direct3D 7 leaves the FPU in single precision for the whole game (control word 0x7f; `cpu.cw = 0x7f`, `x86emu.ts` `p24`; env `M7_CW` overrides the emulator default 0x27f). Every `+ - * / sqrt` result is rounded to float32 whether or not the compiler stored it; sin / cos / atan2 stay double until the next operation; `fcomp; test ah,0x41` treats NaN as `<=`; the decompile lists 3-term sums in a different order than the asm adds them (x, y, z in the asm). A bit-exact port therefore needs `Math.fround` around every single operation. Shared exact helpers: `src/zones/exact.ts` (matrix builders `FUN_0043a5e4/a4a1/a340/a742`, normalise, reflect, rotY, toWorld, multiply), `src/zones/f32math.ts`, `src/zones/common/f32.ts` + `matrix.ts` (incl. `asin24` = the CRT's asin), `src/formats/matrixf32.ts`, `tools/lib/m7-camera-exact.ts`. `src/formats/matrix.ts` `buildMatrix` is NOT exact (double products, 1 ulp off in ~18 % of elements): do not use it where exactness matters.

## x87 control word (WP-INTEGRATION 2026-10-29)

* The executable runs every game-time computation (zone set-up, node updates, particles, the loading card, ...) at control word 0x7f (24-bit precision): Direct3D 7 sets it when the device is created, which precedes the first zone load. Only the CRT start-up would run at 0x27f, and nothing the tests compare happens there. The particle engine (`FUN_0044ec60`, built per zone load, so its `FUN_00454460` sin / cos table accumulates in float32: `a = (float)(a + step)`) and the loading card (`FUN_0040d1be`, drawn while a zone loads) are therefore 24-bit as well.
* `Cpu.cw` still defaults to 0x27f (env `M7_CW` overrides), but nothing relies on the default any more: `createGameCpu` (x86emu.ts, `GAME_CW` = 0x7f) is what `emulateZoneSetup` (src/formats/emusetup.ts: the set-up now runs at 0x7f in the browser too, the earlier statement "emusetup assumes 53 bit" is gone) and every oracle harness use. Three test modules used to assign `process.env.M7_CW` at import time, which leaked into every later test of the same process (x86emu's default-control-word test, particles-oracle, m8-shell-loadcard failed because of that); they set it for their own run only now.
* Ports made exact in this pass: `src/fx/particles/**` (all arithmetic per operation; `r24` for denormal-range velocities), `src/fx/particles/mat.ts` (shared by z08BKD, z07CSI horse, the renderer: now the same order and rounding as `zones/exact.ts`), `src/ui/loadingcard.ts` (`0.05f * dt` rounds before the add), z40aPO (`rate` of the accel sound, asteroid spins, brickbot normalise / yaw, camera easing, wing position through the exact `toWorld`, glide forward step, bounce reflection, HUD gauge), `parachute/util.ts` (`rand(max)` = `(float)((float)(r / 32767) * max)`, `transformPoint`). `m5-audit-z40aPO-emu` is bit exact now (tolerance 0, 14 M comparisons; `APO_TOL` rescales the old tolerances).
